## Executive summary

- SB_LCS reduces stored LCS information by reconstructing rows during traceback. It stores values that cannot be reconstructed in a stack. (PDF p. 3).
- The authors report tests on DNA sequences up to 100 kb. They retain O(MN) time complexity and report lower memory use than full-table LCS. (PDF p. 5).

## Objectives

- The authors aim to reduce forward-pass storage while retaining enough information to construct an optimal LCS. (PDF p. 1).
- The intended memory reduction permits longer DNA inputs for global alignment. (PDF p. 1).

## Arguments

- Only the previous and current rows are needed to compute LCS values. Constructing the LCS also requires information for traceback. (PDF p. 3).
- The authors argue that many earlier row values can be reconstructed from later rows. Only the remaining values need stack storage. (PDF p. 3).

## Analysis

- The baseline stores LCS values in TblV and parent directions in TblP. Full-table traceback storage requires O(MN) memory. (PDF p. 2).
- The Appearances matrix uses O(KM) memory for an alphabet of size K. It supports a constant-time character-occurrence check in a reconstruction rule. (PDF p. 4).
- The authors state that SB_LCS retains O(MN) time complexity. Reconstruction adds some time relative to ordinary LCS. (PDF p. 5).

## Methods

- The forward pass overwrites old rows after testing whether their values can be reconstructed. Stack entries contain a value, column, TRow, and a link to the previous entry in that column. (PDF p. 3).
- Reconstruction processes each row from left to right. Rules use stack values, child-parent relations, neighboring values, and column history. (PDF p. 3).
- Further rules use character occurrences and TRow information. If no rule resolves a value, the method assigns one less than the bottom-neighbor value. (PDF p. 4).
- Preprocessing constructs four bounds from character-equality points. These bounds restrict the region needed during traceback. (PDF p. 4).

## Applications

- SB_LCS accepts two FASTA sequences and supports global alignment of DNA and protein sequences. (PDF p. 5).

## Optimization

- The method stores exceptional values instead of the complete dynamic programming table. (PDF p. 3).
- ColumnView records the latest stack entry for each column. TRow records the earliest row of a same-value run in that column. (PDF p. 3).
- The authors state that the optimal traceback stays within the four bounds. Values outside the required region need not be stacked. (PDF p. 5).

## Evaluation and testing

- The authors tested the SB_LCS program on DNA sequences up to 100 kb using a computer with 512 Mb RAM. (PDF p. 5).
- The reported comparison considers memory use against full-table LCS and qualitative runtime and memory differences against divide and conquer. (PDF p. 5).

## Results

- The authors report a stack of about 1.5 Gb for the large-input tests. They state that ordinary LCS would require more than 10 Gb for the same lengths. (PDF p. 5).
- The authors report memory reductions of up to about tenfold and successful global alignment of inputs up to 100 kb. (PDF p. 5).
- The authors state that SB_LCS is faster than divide and conquer, but uses more memory. (PDF p. 5).

## Limitations and uncertainty

- Some row values cannot be reconstructed and still require stack storage. (PDF p. 3).
- The experimental section gives no numerical runtime comparison or explanation of how the reported 1.5 Gb stack was managed on 512 Mb RAM. (PDF p. 5).
- Combining SB_LCS with divide and conquer is proposed as future work. The reported implementation does not establish that combined result. (PDF p. 5).
