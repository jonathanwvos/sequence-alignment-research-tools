## Executive summary

- Halvade executes read alignment and variant calling in parallel with Hadoop MapReduce. It runs multiple instances of existing tools across cores and nodes. (PDF p. 2).
- The implemented pipeline uses BWA, Picard and GATK for whole genome and whole exome analysis. (PDF p. 2).
- The whole genome benchmark finished in 2 h 39 min on 15 Intel worker nodes and 2 h 44 min on 16 Amazon EMR worker nodes. (PDF p. 5).

## Objectives

- The authors aim to reduce analysis time for a single genome across different cluster configurations. (PDF p. 2).

## Arguments

- The authors argue that read alignment is independent by read and that variant calling is conceptually independent by chromosomal region. (PDF p. 2).
- They argue that multiple tool instances with limited threads can use a node more efficiently than one instance with many threads. (PDF p. 2).

## Analysis

- MapReduce groups alignments by chromosomal region and sorts SAM records by genomic position. This replaces a separate alignment sorting step. (PDF p. 3).
- The authors attribute the longer Amazon runtime to network access to S3. The Intel cluster uses persistent HDFS storage with local input access. (PDF p. 6).

## Methods

- Halvade Uploader interleaves paired reads and divides compressed FASTQ input into approximately 60 MB chunks. Each chunk defines one map task. (PDF p. 2).
- Each mapper streams reads to an alignment tool using the complete reference index. It emits SAM records with keys that contain chromosome, position and region identifiers. (PDF p. 3).
- Reads or read pairs that cross a region boundary are sent to both regions. Each reducer processes sorted reads for one region and produces a VCF file. (PDF p. 3).
- An optional second MapReduce job merges regional VCF files. It keeps overlapping calls with unique names or retains the call with the highest Phred-scaled quality score. (PDF p. 3).

## Applications

- The authors propose use on local hospital clusters to reduce the time between sample collection and diagnosis. (PDF p. 2).
- The implemented pipeline supports whole genome and whole exome variant calling. (PDF p. 7).

## Optimization

- Tests identified approximately 60 MB input chunks as the fastest configuration. This size balances task overhead, workload distribution and local HDFS access. (PDF p. 5).
- The Intel benchmark uses four tasks per node, with six cores and approximately 15.5 GB of memory per task. One task slot is reserved for cluster management. (PDF p. 5).
- The Amazon benchmark uses four tasks per node, with eight cores and 15 GB of memory per task. (PDF p. 6).
- Picard can be replaced by elPrep. elPrep combines preparation steps in one in-memory pass and avoids file I/O between steps. (PDF p. 5).

## Evaluation and testing

- The whole genome benchmark uses NA12878 with 1.5 billion 100 bp paired-end reads and 50-fold coverage. The input comprises two 43 GB compressed FASTQ files. (PDF p. 5).
- The benchmark uses BWA 0.7.5a with aln and sampe, GATK 3.1.1, Picard 1.112, BEDTools 2.17.0 and SAMtools 0.1.19. It uses the GATK hg19 reference and dbSNP resources. (PDF p. 5).
- Scalability tests increase the Intel cluster from one to 15 worker nodes and the Amazon cluster from one to 16 worker nodes. (PDF p. 6).
- The accuracy check compares whole genome variants with a validation set from a sequential GATK Best Practices pipeline run. (PDF p. 7).

## Results

- On the Intel cluster, runtime decreases from 47 h 59 min to 2 h 39 min. The reported speedup is 18.11 and parallel efficiency is 92.1%. (PDF p. 5).
- On Amazon EMR, runtime decreases from 38 h 38 min to 2 h 44 min. The reported speedup is 14.16 and parallel efficiency is 88.5%. (PDF p. 6).
- The exome benchmark finishes in under one hour on eight Amazon worker nodes. Parallel efficiency is approximately 90% on eight nodes and 70% on 16 nodes. (PDF p. 6).
- The authors report more than 99% agreement with the sequential validation set. Almost all differing variants have very low variant scores. (PDF p. 7).

## Limitations and uncertainty

- Some tools produce slightly different results when they process only a subset of the data. (PDF p. 7).
- Amazon runtimes exclude input upload time over the internet. (PDF p. 5).
- Major changes to reduce-phase tools can require changes to Halvade Java code because intermediate formats and processing steps differ between tools. (PDF p. 6).
- The MegaSeq comparison uses different variant callers and annotation steps. The authors also note that core counts and clock rates do not capture all hardware differences. (PDF p. 6).
