## Executive summary

- The method adds run-length-compressed graph-coordinate tags to an FM-index of haplotypes. Queries report distinct matching graph positions. (PDF p. 3).
- Construction combines unique k-mer anchors, graph extension, and haplotype traversal. Chromosome indexes are built separately and merged. (PDF p. 6).
- Sampled tag arrays and an r-index also support coordinate translation between haplotypes that share graph paths. (PDF p. 20).

## Objectives

- The authors aim to preserve haplotype-to-graph mappings without lossy graph transformations or redundant reporting of equivalent positions. (PDF p. 3).
- The construction method aims to control memory use for large pangenomes. (PDF p. 6).

## Arguments

- A haplotype FM-index reports equivalent seeds separately for each haplotype. Direct graph indexes can require costly, lossy transformations. (PDF p. 2).
- Sparse k-mer indexes require a fixed seed length. The authors argue that this imposes a sensitivity–specificity trade-off that FM-indexes avoid. (PDF p. 2).
- Similar suffixes can map to the same graph position. The authors use this property to justify run-length compression of the tag array. (PDF p. 3).

## Analysis

- An FM-index returns a lexicographic interval for a pattern. Document-listing techniques over its tags can then report the matching graph positions. (PDF p. 3).
- Filling tags only through haplotype traversal creates many short runs and gaps during construction. The staged method reduces this intermediate fragmentation. (PDF p. 6).
- The authors attribute sublinear growth in tag runs to shared sequence paths across haplotypes. (PDF p. 19).

## Methods

- Unique k-mers first annotate BWT positions. Extension increases coverage, and traversal of each haplotype fills the remaining gaps. (PDF p. 6).
- A run-length B+ tree stores each tag run as a tag, start position, and length. It supports insertion and merging during construction. (PDF p. 6).
- Chromosome tag arrays are merged using multi-string BWT structure and the r-index mapping from BWT positions to sequence numbers. (PDF p. 6).
- Coordinate translation combines sequence-to-BWT mapping from the r-index with BWT-to-node-boundary mapping from sampled tags. (PDF p. 20).

## Applications

- The bidirectional FMD-index supports query extension in both directions for tasks such as maximal exact match finding. (PDF p. 13).
- The authors propose the index as a basis for haplotype-aware aligners and graph analysis tools. (PDF p. 1).
- Coordinate translation can transfer annotations, variant intervals, and structural features across haplotypes without a linear reference. (PDF p. 20).

## Optimization

- Anchoring and extension construct nearly 95% of the tag array. This reduces the work and memory required by final traversal. (PDF p. 15).
- Separate chromosome construction controls memory and permits parallel processing. The authors report that parallel chromosome indexing can more than halve wall-clock time. (PDF p. 20).
- Tree degree and merge batch size provide memory–CPU trade-offs. Higher tree degrees generally reduce memory use but increase processing time. (PDF p. 19).

## Evaluation and testing

- Tests used bidirectional HPRC v1.1 and v2.0 indexes with 90 and 464 haplotypes. Their indexed sequence lengths were 513 Gbp and 2,633 Gbp. (PDF p. 13).
- Experiments ran in exclusive SLURM allocations on nodes with two AMD EPYC 7662 processors, 256 logical CPUs, and 2.0 TiB RAM. (PDF p. 13).
- Construction used grlBWT output to build the r-index. The construction comparison in Figure 4 excludes grlBWT runtime. (PDF p. 13).
- Query tests processed 10,000 k-mers with lengths from 10 to 2,000, all known to occur in the BWT. Each query found its BWT interval and retrieved all distinct tags. (PDF p. 15).

## Results

- Tag runs increased from 12.7 billion to 26.2 billion between the two datasets. Final tag array sizes were 68.6 GiB and 149 GiB. (PDF p. 13).
- Sampled tag array sizes were 6.9 GiB for v1.1 and 22.8 GiB for v2.0. (PDF p. 13).
- With roughly five times more bases, v2 had about 1.2 times as many BWT runs and twice as many tag runs. (PDF p. 15).

## Limitations and uncertainty

- The bidirectional representation doubles the indexed bases and increases both BWT and tag run counts relative to a unidirectional index. (PDF p. 13).
- Construction of the v2 bidirectional index required about 500 GiB of memory. The authors identify merging as a memory-intensive stage that needs improvement. (PDF p. 19).
- Combined FMD-index and tag array construction takes longer than specialized construction with ropebwt3. Integration with existing read aligners remains future work. (PDF p. 19).
